## 0. 코드 확인으로 발견한 현황

- `api/state.js`: 인증 없이 GET으로 전체 테이블을 읽고 POST의 여러 action을 처리한다. Vercel 서버의 `SUPABASE_SERVICE_ROLE_KEY`는 RLS를 우회할 수 있다. **로그인 UI만 추가하면 타인의 자료가 노출된다.**
- `supabase/schema.sql` / `supabase/upgrade-v3.sql`: 현재 테이블에는 사용자 소유자 `user_id`가 없다. `pds_weekly_reviews.week_start`가 전역 UNIQUE이고 `pds_color_swatches.color`가 전역 PK다.
- `pds_update_plan`, `pds_complete_task`, `pds_create_next_plan`, `pds_save_weekly_review`는 SECURITY DEFINER 계열 서버 함수이므로 소유자 확인/실행 권한을 전체 검토해야 한다.
- 기존 T06 데이터를 계정에 할당하기 전 정확한 백업과 행 수 비교가 필수다.

## 1. 작업 진행 조건 (먼저 충족)

- [ ] 기존 다이어리의 '전체 데이터 내보내기' JSON을 로컬 비공개 폴더에 저장했다. 공개 저장소에 올리지 않았다.
- [ ] **DB 스키마+데이터 백업**을 Supabase 백업 기능 또는 `pg_dump`로 확보하고 실제 복원 가능성을 확인했다. JSON은 DB 백업을 대체하지 않는다.
- [ ] 실 서비스에 대한 자동 프리뷰 배포 설정을 확인했다. **테스트 브랜치를 기존 운영 DB에 연결해 인증 마이그레이션을 실행하지 않는다.**
- [ ] T06 제출 당시의 **정확한 commit SHA**를 제출 자료와 비교해 고정했다 (위 SHA는 현재 main 기준점일 뿐 제출 당시 값인지 미확인).
- [ ] 격리된 시험 DB/테스트 Vercel 프로젝트를 마련하고 **테스트용 더미 데이터**만 사용한다.

## 2. 인증·인가 방식 (선택 초안)

- 인증 서비스: **Supabase Auth** (실제 SDK/서비스 버전·해시 방식은 도입 때 검증 후 문서화).
- UI: 이메일 회원가입/로그인/로그아웃. 로그인 전엔 자료 화면 렌더링 금지.
- 서버: 매 요청마다 검증된 세션에서 사용자 ID를 구하고, 요청의 `user_id` 또는 다른 헤더/URL을 절대 신뢰하지 않는다.
- 데이터: PostgreSQL 소유자 컬럼 + RLS. `service_role` 사용 경로는 계정별 필터 및 관계 소유자 검사를 명시적으로 수행하거나, 사용자 컨텍스트 RLS가 강제되는 경로로 변경한다. 가장 안전한 목표는 사용자 위임 JWT+RLS(필요한 범위만 허용).
- 유의사항: Supabase의 access token은 로그아웃/비밀번호 변경 직후에도 만료 전까지 유효할 수 있다. T07-C114를 만족하려면 서버 측 세션 상태/무효화 전략이 별도로 설계되고 **같은 이전 인증값으로 재요청해 401**을 증명해야 한다. 단순 브라우저 토큰 삭제는 불합격.

## 3. 데이터 소유권 이전 계획

1. 모든 기존 테이블, FK/UNIQUE/PK, 트리거, RPC, RLS/GRANT의 전체 스냅샷을 기록한다.
2. **별도 시험 DB에서만** `user_id uuid`(사용자 식별)를 부모/자식 리소스에 점진적으로 추가하고 기존 레코드의 관계를 유지한다.
3. T06 공개 데이터는 백업된 상태에서 **확인된 본인 Auth user UUID**에만 할당한다. 계정 생성 이후 별도 일회성 이관 절차를 검증하고 적용한다. 유실/중복 여부는 이관 전후 row count와 PK 목록으로 확인한다.
4. `pds_weekly_reviews`의 전역 UNIQUE(week_start)는 사용자별 UNIQUE(user_id,week_start)로, `pds_color_swatches`의 전역 PK(color)는 사용자별 UNIQUE(user_id,color)로 변경한다. 사용자의 기존 색상 내역은 소유자에게 이관한다.
5. 계획↔할 일↔셀/로그/완료↔회고 연결 FK에서 다른 사용자 ID를 끼워 넣는 요청까지 차단한다.
6. SECURITY DEFINER 함수에 소유자 검사, search_path 고정, 허용된 role만 EXECUTE가 가능한지 검토한다. 한 레코드 조회와 **목록**, RPC, 내보내기, 계정 삭제 경로 모두 확인한다.
7. 검증한 마이그레이션을 운영에 반영하기 전 유지보수·일시 쓰기 차단 계획을 별도 수립한다. 공개 `/api/state`가 남지 않도록 인증 전환을 함께 배포한다.

## 4. 보안 증거 표 (지금은 미실행)

요청/응답 실제 값만 기록. 계정 이메일은 별칭 A/B로, 비밀번호·JWT·쿠키·서비스키는 **원문 금지, 마스킹**.

| 시험 | 주소·메서드 | 성공 기대 | 거절 기대 | 실제 증거 |
| --- | --- | --- | --- | --- |
| 익명 목록 | GET /api/state | 로그인 상태 200 | 비로그인 401 | 미실행 |
| 로그아웃 무효화 | 동일 URL·메서드·과거 인증값 | 로그아웃 전 200 | 로그아웃 후 401 | 미실행 |
| 비밀번호 변경 무효화 | 동일 URL·메서드·과거 인증값 | 변경 전 200 | 변경 후 401 | 미실행 |
| A→B, B→A 읽기 | 보호된 GET | 내 자료 200 | 남의 자료 403/404 | 미실행 |
| A→B, B→A 수정 | 보호된 PATCH/POST | 내 자료 성공 | 남의 자료 403/404 | 미실행 |
| A→B, B→A 삭제 | 보호된 DELETE/POST | 내 자료 성공 | 남의 자료 403/404 | 미실행 |
| 타인 user_id 변조 | URL·헤더·본문의 소유자 변조 | 내 자료만 | 타인 결과 없음 | 미실행 |
| 목록·내보내기 | 계정 A/B 별도 로그인 | 내 항목만 | 타인 ID 0건 | 미실행 |
| 거절 전후 데이터 불변 | DB에서 상대 계정 건수/PK 비교 | 변화 없음 | 0건 변조 | 미실행 |

## 7. 비밀정보 정책

- 비밀번호, 비밀번호 해시 전체, 쿠키, access/refresh token, 서비스키, .env 원문을 공개 repo·증거 화면·채팅·제출물에 **절대 포함하지 않는다**.
- 채점용 비밀번호 해시는 포맷과 상이한 salt를 알 수 있도록 **앞부분만 보이는 마스킹 예시** 또는 **시험 전용 계정의 비민감 검증용 결과**로 제시한다. 원문 출력 요구와 비밀값 금지 사이의 해석은 심사 기준과 조율한다.
- 실제 테스트 기록 없이 '차단 성공' 또는 '인증 완료'라고 표시하지 않는다.
