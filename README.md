## 이번 수정

1. 연결된 할 일의 우선순위는 연결 계획의 우선순위를 **자동 상속**합니다. 기존 연결 할 일의 값도 업그레이드 시 맞춰지고, 계획을 수정하면 한 트랜잭션 안에서 연결된 할 일 우선순위가 변경됩니다. **연결 없는 할 일은 독립적인 우선순위**를 갖습니다.
2. 주간 계획 카드 더블클릭 → 계획 수정 → **계획 삭제**. 소프트 삭제로 주간 계획 목록에서 숨기지만 `pds_plans` 데이터·수정 이력·연결된 할 일·실행 기록은 DB에 보존됩니다. 삭제된 계획에 새 할 일 연결은 불가합니다.
3. **나의 기록** 탭 추가: 주간 돌아보기는 그 주에 **한 장만** 저장합니다. `오늘의 작은 발견`과 `다음 주에 다르게 해볼 것`을 같은 날짜 카드 안에 합치고, 날짜 크게 한 번, 카테고리 제목은 **Muted Rose `#B56872`**, 본문 전체를 가로 줄노트로 표시합니다. 긴 글은 자동 높이 확장. 작성하지 않은 주는 기록이 생성되지 않고 경고하지 않습니다. 새 주에는 새 입력칸이 준비됩니다. 카드마다 배경·날짜 글자색 변경 가능.
4. 할 일 상세의 **자주 쓰는 색상** 원형 버튼. 기존 할 일에 저장된 색상을 첫 번째 목록에 불러오고, 저장한 새 색상도 Supabase에 누적합니다. `pds_color_swatches`는 공개 앱 전체의 공통 색상 기록입니다.

## 이미 배포된 Supabase 프로젝트 업데이트 — 실행 순서

1. **먼저 백업:** 현재 웹사이트 → **↧ 전체 데이터 내보내기**로 JSON 파일을 다운로드하고, 필요시 Supabase Table Editor에서도 기존 테이블 데이터를 별도 내보냅니다. 비밀키는 파일에 포함하지 않습니다. 나중에 실수했을 때 현재 기록을 대조할 수 있도록 보관합니다. 과제 데이터가 공개 상태라는 사실을 기억하세요.
2. **Supabase → SQL Editor → New query**에서 오직 **`supabase/upgrade-v3.sql`** 전체를 복사해 실행하고 `Success`를 확인합니다. 기존 `schema.sql`을 반복 실행하거나 기존 테이블을 삭제하지 마세요. 이 스크립트는 새 테이블 두 개(`pds_weekly_reviews`, `pds_color_swatches`)와 `pds_plans.deleted_at`을 추가하고, 우선순위 전파 RPC 및 색상 저장 트리거를 교체합니다.
3. **기존 기록 보존 규칙:** 모든 원본 계획별 돌아보기(`pds_reflections`)는 DB에 유지됩니다. 새 아카이브에 이전 돌아보기를 가져올 때 같은 주차에 여러 계획 기록이 있다면 최근 수정된 1건만 새 주차 카드로 복사하고 나머지 원본도 `pds_reflections`에 그대로 보관합니다. `pds_plan_versions`, `pds_tasks`, `pds_logs`, `pds_completion_events`는 삭제하지 않습니다.
4. GitHub 저장소 `jennajiminkim/plandosee-web-diary`의 **최상위**에 업데이트된 프로젝트 파일을 업로드합니다(기존 파일 대체 + 신규 `supabase/upgrade-v3.sql`, `contracts/pds-schema-v3.json` 추가). GitHub `main` 변경 시 Vercel이 자동 재배포합니다. **절대로 SQL 파일을 웹사이트에서 실행하지 말고 Supabase SQL Editor에서 실행**하세요.
5. Vercel **Deployments → Ready** 확인 후 웹사이트 새로고침. 기존 환경변수 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`는 **그대로 유지**합니다. GitHub나 채팅에 비밀키를 게시하지 마세요.
6. 아래 항목을 실제 데이터로 검증합니다. 문제가 생기면 기존 Main 코드로 롤백하기 전 데이터 및 DB 구조 호환성을 확인하세요. 구형 앱은 새로운 테이블이 추가돼도 동작하므로 **SQL 먼저 → 새 코드 배포** 순서가 중요합니다.

## 1. 빠른 배포 순서

1. 이 ZIP을 풉니다. GitHub에서 공개 저장소를 만들고, ZIP 안의 `plan-do-see-task6/` **폴더 안 모든 파일**을 저장소 **최상위**에 올립니다. 저장소에 `.env` 파일, Supabase 키, 비밀번호를 올리지 마세요. 공개 저장소 설정을 확인합니다.
2. Supabase 프로젝트를 준비합니다. SQL Editor에서 `supabase/schema.sql` **전체 내용**을 **한 번 실행**합니다. 이미 과제 6의 구형 DB를 실행했다면 먼저 백업하고 `supabase/migrate-from-old-schema.sql`을 실행한 다음 `schema.sql`을 실행합니다. 기존 DB의 데이터가 있는 경우 새로고침 전에 DB의 제약 조건과 스키마가 업데이트되었는지 확인하세요.
3. [Vercel](https://vercel.com/new) → Add New Project → GitHub 저장소 Import → 프레임워크 설정 **Other(기타)** → 루트 디렉터리 프로젝트 최상위 → 배포합니다. Functions에서 Node.js 20+ 환경을 사용합니다. 리포지토리 루트에 `index.html`, `app.js`, `style.css`, `api/state.js`, `vercel.json`이 보여야 합니다.
4. **Vercel 프로젝트 Settings → Environment Variables**에 다음 두 값을 등록합니다. 값은 **Vercel 화면에서만** 입력하고, GitHub, SQL, 브라우저 코드나 채팅에 붙여 넣지 않습니다.
   - `SUPABASE_URL`: Supabase → Project Settings → API → Project URL (`https://…supabase.co`)
   - `SUPABASE_SERVICE_ROLE_KEY`: Supabase → Project Settings → API Keys → **Secret API key (`sb_secret_...`) 권장** 또는 기존 **legacy service_role JWT** (Vercel 환경변수에만 설정). 신규 secret key는 `apikey` 헤더에만 전송합니다.
5. 환경변수 등록 후 Vercel → Deployments → **Redeploy**합니다. 브라우저에서 `https://배포도메인.vercel.app` 접속하고 **새 시크릿 창**에서도 인증 없이 열리는지 확인합니다.
6. 초기 DB에는 기록이 없습니다. 사용자가 **직접 실제 계획 1개, 그 계획에 연결된 실제 할 일 5개 이상, 실행 기록 3개 이상**을 입력해야 합니다. `아래 2. 실제 데이터 작성` 참고.

> `index.html`만 더블클릭하면 정적 디자인은 보일 수 있지만 서버 API(`/api/state`)를 호출할 수 없어서 **저장 기능은 동작하지 않습니다**. 제출용 실제 검증은 Vercel 주소에서 하세요. 이 ZIP 안에는 비밀키 원문이 없습니다.

## 2. 실제 데이터 작성 가이드

개인적으로 실제로 진행한 항목만 선택하세요. 다음은 **입력 방향의 예**이며 DB에 자동으로 들어가는 샘플 자료가 아닙니다.

- 계획 예: `정보보안 자격증 이론 복습` — 이번 주 실제 학습 기간, 숫자 우선순위, 실제 달성 기준과 예상 소요 시간을 작성
- 그 계획의 할 일 5개 이상 예: `네트워크 기초 개념 정리`, `인증 방식 복습`, `실습 명령어 복습`, `오답노트 정리`, `연습문제 풀이`. **사용자가 이번 주 실제로 수행한 항목만 등록**하세요.
- 실행 기록 3개 이상: 주간 표에서 할 일의 날짜 셀 선택 → `+ 실행 기록 추가` 펼치기 → 실제 시작·종료 시각과 진행 지점, 막힌 이유(있다면)를 작성. 실행 기록의 실제 분 수는 입력 시각으로 계산됩니다.
- 할 일 상세에서 `연결된 계획 (선택) → 없음 · 자유로운 할 일`을 선택하면 산책·취미처럼 계획이 없어도 기록할 수 있습니다. 이 항목은 다른 계획의 집계에 포함되지 않습니다.
- `주간 돌아보기`에서 집계 숫자 선택 → 해당 근거 할 일 확인. `시간 기록`의 수치 클릭 → 시간별 기록 보기 → 할 일 실행 로그로 이동. `다음 주에 다르게 해볼 것` 작성 → **돌아보기 저장** → **다음 계획으로 가져오기**.
- 계획 수정 이력은 주간 계획 카드 **더블클릭** 또는 연결된 할 일 → `계획 상세 및 수정 이력`을 통해 확인할 수 있습니다.

## 3. 검증 순서 및 증거

**지켜야 할 기준: '코드가 있다'와 '실제로 통과했다'는 다릅니다.** `evidence/verification-checklist.md`에서 실제 수행 후 확인 결과를 기록하세요.

**카드 1:** 계획 만들기 → 계획 수정 전 스크린샷 → 우선순위나 예상 시간을 고친 뒤 같은 ID의 `pds_plan_versions.snapshot`과 수정 이력에 이전 값이 남았는지 확인 (`C04~C08`).

**카드 2:** 연결된 할 일 5개를 추가하고 편집·완료·되돌리기·삭제 테스트. 검색·필터·우선순위/마감일/이름 정렬 결과 확인. 동일 값의 정렬 순서는 우선순위 → 생성 시각 → ID 등 고정된 보조 기준 적용 (`C09~C20`).

**카드 3:** 실행 기록 세 가지 이상에 시작·종료·분·막힘을 저장하고, 계획의 예상 값 불변 확인. 같은 완료 작업을 빠르게 두 번 눌러도 `pds_completion_events`의 `task_id` 유일키와 서버 트랜잭션에 의해 1건만 남는지 확인 (`C21~C27`).

**카드 4:** 계획별 4개 집계 수치와 시간 3개 수치 확인. 지연 날짜는 **서울 오늘** 기준, 완료한 할 일은 지연에서 제외, 막힘은 '막힘 메모가 하나라도 있는 할 일'당 1개. 각 수치의 근거 기록 이동, 다음 계획으로 내용 전달 (`C28~C33,C83`).

## 4. API, 스키마, 공개/보안 정책

- `GET /api/state`: 9개 데이터 종류(계획·계획 버전·할 일·일별 체크·실행 기록·완료 이벤트·돌아보기·주간 기록·색상)를 JSON으로 조회합니다 (종류별 3,000개 한도; 과제 규모 기준).
- `POST /api/state` body `{"action":"task.create","data":{...}}`: `plan.create/update`, `task.create/update/delete/complete/reopen`, `cell.save`, `log.create/delete`, `reflection.save/next`를 지원합니다.
- 프런트 코드 `app.js`는 비밀키를 모르고 같은 출처의 API만 호출합니다. Supabase `anon/authenticated` 직접 권한은 철회하고 RLS 활성화. Supabase 신규 키는 `Authorization: Bearer`에 보내면 JWT 오류가 나므로 서버에서 `apikey` 헤더만 사용합니다. Vercel API 서버만 service role을 사용합니다.
- **주의:** 로그인 없는 공개 쓰기 API는 허가되지 않은 변경이나 자동화된 남용을 막지 못합니다. 이 한계는 과제 명세상 의도된 것이며 과제 7에서 인증·권한·데이터 분리를 구현해야 합니다. 민감한 데이터를 넣지 마세요. 이 과제에서는 비밀키 비공개와 DB 직접 접근 차단만 적용합니다.
- **최종 운영 DB의 9개 테이블·컬럼·관계·날짜 규칙:** 과제 6 지정 경로인 [`contracts/pds-schema-v2.json`](contracts/pds-schema-v2.json)에 v3 확장 사항까지 반영했습니다. 동일한 현재 구조의 상세 v3 문서는 [`contracts/pds-schema-v3.json`](contracts/pds-schema-v3.json)입니다. v2 파일명은 과제 명세의 지정 경로를 유지하기 위한 것입니다.
- 시간: 날짜 값은 `YYYY-MM-DD`, 실행 시각은 `timestamptz` UTC 인스턴트; **실제 시간은 분 단위**, **차이 = 실제 − 예상**. 지연 기준은 Asia/Seoul의 날짜.
- SQL RPC 세 함수 `pds_update_plan`, `pds_complete_task`, `pds_create_next_plan`은 서버 동시 요청 시 데이터 정합성을 보호합니다.
- `pds_tasks.plan_id`는 선택 사항이며 NULL 가능합니다. 삭제는 `deleted_at`에 시각을 쓰는 소프트 삭제입니다.

## 6. 비밀값 점검

- `grep -RniE 'SUPABASE_SERVICE_ROLE_KEY|service_role|sb_secret_' . --exclude=README.md --exclude='.env.example'` 명령으로 **키 변수명이나 문구**는 정상적으로 검색될 수 있지만, 키 **실제 값**이 들어간 소스는 없어야 합니다. 특히 `.env`를 Git 커밋하지 마세요.
